## 2. Logic Chain

1. **Signature Verification Hierarchy Traversal:**
   When Adobe Acrobat opens a digitally signed PDF, its cryptographic verification engine (`Adobe.PPKLite`) traverses the interactive form tree:
   $$\text{Catalog (/Root)} \longrightarrow \text{AcroForm} \longrightarrow \text{Fields [ ]} \longrightarrow \text{Field (/FT /Sig)} \longrightarrow \begin{cases} \text{Value (/V)} \longrightarrow \text{Sig Dict (/Type /Sig)} \\ \text{Widget Annot} \longrightarrow \text{Appearance (/AP)} \longrightarrow \text{Normal (/N Form XObject)} \end{cases}$$

2. **Divergence in Specification vs. Acrobat Implementation:**
   - **ISO 32000-1:2008 Clause 8.10.1 (Table 95):** Defines the `/Resources` entry on a Type 1 Form XObject as *"Optional but strongly recommended"*, specifying that if omitted, the Form XObject shall inherit resources from the graphics state in effect at the point where it is invoked.
   - **Forgiving Viewers (Chrome PDFium, Mozilla PDF.js):** Render the document content stream and visual annotations purely as graphical elements, adhering to the ISO fallback rule without validating the appearance layer structure.
   - **Adobe Acrobat Verification Engine:** During digital signature verification, Acrobat executes a strict integrity parser over the visual appearance hierarchy (`/AP << /N ... >>`). Acrobat's internal signature rendering routine does **not** fall back to page resources; it explicitly calls its internal dictionary accessor (`dict->GetDict("Resources")` or equivalent) on the `/N` Form XObject. When the `/Resources` key is omitted, the accessor encounters `null`/missing instead of a dictionary, triggering the type-assertion failure: **`Expected a dict object`**.

3. **Sub-XObject Layer Traversal Bug in Acrobat:**
   When a signature appearance Form XObject invokes an image XObject (`/SigImg Do`), Acrobat's layer-inspection routine traverses down into the referenced XObject (`imgObjNum`). Because Acrobat expects all appearance layers to be structured containers with their own resource definitions, it queries `/Resources` on the referenced Image XObject. Because standard Image XObjects omit `/Resources`, Acrobat fails with the identical `"Expected a dict object"` error. Providing an explicit empty resource dictionary (`/Resources << >>`) on both Form XObjects and embedded Image XObjects satisfies Acrobat's internal parser.

4. **Multi-Widget Architecture for Dual-Copy CS Form 48:**
   Civil Service Form No. 48 contains Copy 1 (left) and Copy 2 (right) on the same page. ISO 32000-1 Clause 12.7.3 mandates that a single field with multiple physical representations must be structured as:
   - A single non-terminal parent field (`/FT /Sig`, `/T`, `/V`, `/Kids [ child1 child2 ]`)
   - Terminal child widget annotations (`/Type /Annot`, `/Subtype /Widget`, `/Parent <parentRef>`, `/Rect`, `/AP << /N ... >>`)
   - Child widgets must **never** repeat `/FT`, `/T`, or `/V`.
   - In both Pass 1 (first-signature) and Pass 2+ (incremental), every terminal child widget's `/AP /N` Form XObject must include `/Resources << >>`.

## 7. Conclusion

1. **Root Cause Identified:** The Adobe Acrobat verification error `"Expected a dict object"` occurs because Adobe Acrobat's signature appearance parser requires that every visual appearance stream Form XObject (`/AP /N`) and every XObject invoked within it possesses an explicit `/Resources` dictionary.
2. **First-Signature Mode Defect:** In `server/services/pnpkiSigningService.ts` (line 1843), the empty appearance stream is generated via `pdfDoc.context.stream("q\nQ\n", { Type: "XObject", Subtype: "Form", BBox: [0, 0, rw, rh] })` without `Resources: {}`. Serializing this creates a Form XObject lacking a `/Resources` entry, which directly causes Acrobat to fail with `"Expected a dict object"` upon document load.
3. **Incremental Mode Defect:** In `appendSignatureIncremental` (line 1241), Image XObjects (`imgObjNum`) created for visual signatures omit `/Resources << >>`. When Acrobat verifies the visual appearance and traverses down into `/SigImg Do`, it expects a `/Resources` dictionary on the image object and crashes.
4. **Resolution Path:**
   - In First-Signature Mode: Pass `Resources: {}` to `pdfDoc.context.formXObject` or `pdfDoc.context.stream` (emitting `/Resources << >>`).
   - In Incremental Mode: Add `/Resources << >>` to Image XObject dictionaries (`imgObjNum` and `smaskObjNum`).
   - In AcroForm: Ensure `/SigFlags 3`, `/DR`, and `/DA` are consistently present across both single and multi-pass signing.
   - Synchronize identical fixes across `dict-monitoring/server/services/pnpkiSigningService.ts` and `dict-dtr-generator/server/services/pnpkiSigningService.ts`.
